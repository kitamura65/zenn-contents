Claude Code の会話は、`~/.claude/projects/` にセッション1つにつき1ファイルで全文が残っています。ここを読めば「自分が実際に何を繰り返しているか」が分かるので、CLAUDE.md や Skill に何を書くべきかを勘ではなく実績で決められる——という話をちらほら見かけるようになりました。

自分も一度やっていて、そのときのメモには、42セッションぶん、プロンプト767件を読んだと書いてあります。先日それを記事にしようとして、同じ条件で数え直しました。

36セッション・プロンプト555件。 200件以上合いません。

ログは既定30日で自動削除されるので、最初は「消えたぶんだな」と思いました。確かめるために、当時のコードを引っぱり出して今のログに流し直したら、そちらは729件でした。

| 同じ日の、同じログを | 件数 |
|---|---|
| 当時のコードで数える | 729 |
| 今のコードで数える | 555 |

**同じログを、抽出コードだけ変えて数えて174件ずれます。**消えたぶんではありません。自分が「自分のプロンプト」として何を数えていたかが変わったぶんです。

（手元のログは全部で40セッションありますが、この36セッションは最初に数えたときと同じ5プロジェクトに絞ったものです）

追いかけているうちに、もう1つ分かったことがあります。**この「30日」はファイルの更新日時（mtime）で測られていて、会話の中身の日付ではありません。**（mtime は modify time の略で、そのファイルが最後に書き換えられた日時のこと。エクスプローラーの「更新日時」、`ls -l` に出てくるあれです） なので「直近1ヶ月ぶんのログを見た」と言うとき、その1ヶ月は自分で選んだ期間ではないし、そもそも期間ですらない可能性があります。

同じことをやろうとしている人向けに、この2つの落とし穴を書きます。実際に使った抽出スクリプトも置いておきます。

## 前提：ログの置き場所と量

正確なパスは `~/.claude/projects/<パス由来のスラッグ>/<セッションID>.jsonl` で、中身は1行1JSONです。履歴から過去セッションを開けるのは、これを読んでいるからです。

手元は全部で40セッション・63.1MB でした（2026-08-26 時点）。ツールの実行結果やファイルの中身が大半なので、自分が打ったプロンプトだけを抜くと 194KB・589件。1/333 になります。この量なら通しで読めます。

## 1. 減ったぶんの大半は、消えたのではなく数え方の違いだった

冒頭の内訳をどう出したかから書きます。

最初に数えたときのスクリプトは使い捨てにしていたのですが、幸いその作業自体がセッションログに残っていたので、コードも実行結果も丸ごと復元できました。ログを読む作業のログが残っているのは、こういうとき助かります。

当時のコードを今のログに流し直すと、方法の差と削除の差を分けられます。同じコードで新旧のログを比べれば削除のぶんだけが出るし、同じログに新旧のコードをかければ方法のぶんだけが出ます。

| | セッション | プロンプト |
|---|---|---|
| A 当時のコード × 当時のログ（2026-08-19） | 42 | 767 |
| B 当時のコード × 今のログ | 36 | 729 |
| C 今のコード × 今のログ | 36 | 555 |

3つとも同じ5プロジェクトに絞っています。

A→B は「消えたぶん」ではありません。その間に新しい会話も増えているので、-38 は消えた量と増えた量の差し引きです。セッション数が 42→36 に減っている一方で件数が38しか減っていないのは、増えたぶんが相殺しているからで、実際に消えた量はこれより大きい。ここは分離できませんでした。

分離できるのは B→C のほうです。同じ日の、同じログを、コードだけ変えて数えている。差の174件は、まるごと数え方の差です。

差の正体は、エディタが送ってくる状態通知でした。VS Code の拡張から使っていると、「今このファイルを開いています」という情報が `<ide_opened_file>`、選択範囲が `<ide_selection>` というブロックで会話に混ざります。自分が打った文章とは別のブロックですが、同じエントリの中に同居しているので、素朴に「テキストブロックを全部拾う」と1件ずつ数えられてしまう。

落ちた174件のうち162件がこれでした。残りは通知やスラッシュコマンドの展開です。

### `type === "user"` だけでは足りない

`type` が `user` のエントリを全部拾えばいい、と思っていました。手元では5205件あります。そのうち実際に自分が打ったものは589件でした。

| エントリ単位で弾くもの | 件数 |
|---|---|
| `toolUseResult` を持つ（ツールの実行結果） | 4541 |
| `isMeta: true`（内部メッセージ） | 49 |
| `origin.kind` が `human` 以外（タスク通知など） | 19 |
| 残り＝自分が打ったもの | 589 |

**8割以上がツールの実行結果です。**ファイルを読んだ、コマンドを叩いた、その戻り値が全部 `user` として記録されている。ここを弾かないと桁が変わります。

エントリを絞ったあとにも、まだ混ざります。1つのエントリの中に複数のテキストブロックが入っていて、自分が打った文章の隣に別のものが並んでいるためです。

| ブロック単位で弾くもの | 件数 |
|---|---|
| `<ide_opened_file>` / `<ide_selection>` など、エディタが送る状態通知 | 169 |
| `[Request interrupted…]` のような、Claude Code が差し込む合成メッセージ | 6 |

最初に数えたときに取りこぼしていたのは、この下の段でした。エントリ単位のフィルタは当時も入っていて、ブロック単位のほうが抜けていた。

もう1つ `isSidechain: true`（Subagent 宛ての指示）も弾くようにしていますが、手元では1件も引っかかりませんでした。Subagent の会話は `<セッションID>/subagents/` に別ファイルで置かれていて、トップレベルの `.jsonl` には入ってこないためです。そちらまで読むなら要ります。

なお `origin.kind` は、手元のログでは 2.1.211 以降のエントリにしか入っていませんでした（いつ追加されたのかは、公開されている情報では確認できていません）。それより前のログには無いので、古いところまで遡るなら他の条件で判定する必要があります。手元の589件のうち43件が、この「フィールドが無い」ものでした。

### 抽出スクリプト

依存なしの Node スクリプトです。Claude Code 自体が Node で動くので、使っている人の手元には必ず Node があります。

```js
// extract-my-prompts.mjs — 自分のセッションログから、自分が打ったプロンプトだけを抜き出す
//   node extract-my-prompts.mjs > my-prompts.md
import fs from "node:fs";
import path from "node:path";
import os from "node:os";

const ROOT = path.join(os.homedir(), ".claude", "projects");

// プロンプトに見えて、そうではないブロック（IDEの状態通知・タスク通知・スラッシュコマンド展開）
const NOISE =
  /^\s*(?:<(system-reminder|ide_opened_file|ide_selection|task-notification|command-name|command-message|command-args)>[\s\S]*?<\/\1>\s*)+$/i;
// ツール実行を中断したときに Claude Code 自身が差し込む合成メッセージ
const SYNTHETIC = /^\s*\[(Request interrupted|Tool use was rejected)/;

for (const project of fs.readdirSync(ROOT)) {
  const dir = path.join(ROOT, project);
  if (!fs.statSync(dir).isDirectory()) continue;

  for (const file of fs.readdirSync(dir).filter((f) => f.endsWith(".jsonl"))) {
    for (const line of fs.readFileSync(path.join(dir, file), "utf8").split("\n")) {
      if (!line.trim()) continue;
      let e;
      try { e = JSON.parse(line); } catch { continue; }

      if (e.type !== "user") continue;              // assistant・内部イベントを捨てる
      if (e.isMeta) continue;                       // 内部メッセージ
      if (e.isSidechain) continue;                  // Subagent 宛ての指示。自分が打ったものではない
      if (e.toolUseResult !== undefined) continue;  // ツールの実行結果
      if (e.origin && e.origin.kind !== "human") continue; // 通知など（2.1.211 以降のみ）

      const c = e.message?.content;
      const blocks =
        typeof c === "string" ? [c]
        : Array.isArray(c) ? c.filter((b) => b.type === "text").map((b) => b.text)
        : [];
      const text = blocks
        .filter((t) => t.trim() && !NOISE.test(t) && !SYNTHETIC.test(t))
        .join("\n")
        .trim();
      if (!text) continue;

      // 区切りに ### を使わないこと。プロンプト本文に Markdown の見出しが普通に入っている
      console.log(`\n@@ ${project} / ${file.slice(0, 8)} / ${e.timestamp?.slice(0, 10) ?? "?"}`);
      console.log(text);
    }
  }
}
```

```
node extract-my-prompts.mjs > my-prompts.md
```

**出力には顧客名・案件名・認証情報が普通に混ざります。** リポジトリに置かないでください。`.gitignore` に頼るより、そもそもリポジトリの外に出すほうが安全です。抽出結果を別のAIに読ませる場合はなおさら気をつけてください。

細かい話をもうひとつ。この数字には測定しているセッション自身のログも含まれます。走らせている間もログは書き込まれ続けるので、2回続けて実行すると少し増えます。記録に残すなら測定日をセットで書いておくのが無難です。

## 2. 「直近1ヶ月ぶん」は、たぶん自分で選んでいない

セッションログの保持期間は `settings.json` の `cleanupPeriodDays` で決まります。既定30日は公式ドキュメントに書かれています。

> Claude Code clients store session transcripts locally in plaintext under `~/.claude/projects/` for 30 days by default to enable session resumption. Adjust the period with `cleanupPeriodDays`.
> —— [Data usage](https://code.claude.com/docs/en/data-usage)

ここまでは既に書かれている話です。

ただ、公式ドキュメントは「`cleanupPeriodDays` より古くなったファイルを削除する」としか書いていません。何をもって「古い」とするかまでは書かれていない（[Explore the .claude directory](https://code.claude.com/docs/en/claude-directory) の "once they're older than `cleanupPeriodDays`"）。冒頭に書いた mtime の件は、そこを実測して出てきました。

手元のログを調べるとこうなっていました。

| | 値 |
|---|---|
| 現存ファイルの mtime の最古 | 29日前 |
| 現存ファイルの本文の最終メッセージの最古 | 57日前 |
| 現存ファイルの本文の最初のメッセージの最古 | 74日前 |

mtime の最古がちょうど29日前で、30日の境界に張り付いています。一方、最後にやりとりしたのが57日前というセッションが普通に残っている。最終メッセージ時刻で切っているなら、とっくに消えているはずです。

もう1つ、いちばん古い会話を持つファイルを個別に見ると、妙なことになっていました。

```
最初のメッセージ : 2026-06-12T06:23:42Z
最後のメッセージ : 2026-06-29T08:17:37Z
mtime            : 2026-07-27T01:48:53Z
```

**中身が1行も増えないまま、更新日時だけが27.7日ぶん進んでいます。**何が触ったのかは分かりませんでした（同じ日に他のファイルの mtime もまとまって動いているので、バージョン更新まわりの処理を疑っていますが、確かめられていません）。ログを読むだけでは mtime は動かないので、何かが書き込んではいるはずです。

ここから先は推測です。判定が mtime なら、使い続けているセッションは30日を過ぎても消えず、その中には初日の会話がそのまま残っているはず。逆に、短期間で放置したセッションは中身が新しくても消えるはず。ただし手元で最長の利用スパンは22日で、30日を超えて使い続けたセッションは1件もありませんでした。前者の実例は確認できていません（後者は、消えたファイルが見えない以上そもそも観測できません）。

確かなのは、「直近30日ぶんの会話が読める」ではなかった、というところまでです。

これが効いてくるのは、ログを数えて何かを決めるときです。「直近1ヶ月ぶんのログを見た」と書くとき、その1ヶ月は自分で選んだ期間ではないかもしれないし、そもそも期間ですらないかもしれない。**「使っていない」ように見えるものが、単に窓の外にあるだけ**という可能性は潰しておいたほうがいいと思います。四半期に1回やるような作業は、この方法では構造的に候補に上がりません。

手元では90日に伸ばしました。

```json
{
  "cleanupPeriodDays": 90
}
```

「全部残したい」と `0` を入れたくなるところですが、公式ドキュメントによると最小値は1で、`0` はバリデーションエラーになります（同じく [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)）。無期限にはできません。

ただし保持期間を伸ばすということは、ログに混ざっている顧客名や認証情報がローカルに残り続ける期間を伸ばすということでもあります。ディスクよりそちらのほうが判断材料になると思います。

### 実際に、根拠が1つ消えていた

最初の棚卸しのとき、AIが根拠として引用してきたプロンプトがいくつかありました。そのうち1つを今のログで検索したら、出てきませんでした。元のプロンプトが入っていたセッションのほうが先に消えたようです。

残っているのは、AIがそれを引用した6日前のログだけ。引用のほうが原文より長生きしている状態になっていました。ログを根拠に何かを決めるなら、決めた理由のほうを先に自分の手元へ書き出しておいたほうがよさそうです。

## で、棚卸しの結果はどうだったか

本題からは外れますが、そもそもこれを始めた動機のほうも簡単に書いておきます。

Skill の追加候補として `/commit-push-pr`・`/techdebt`・`/morning-sync` の3つをメモしてあったのですが、589件を検索して3つとも0回でした。存在しない需要を3つ書いていたことになります。

代わりにログにはっきり出ていたのは、メモのどこにも書いていなかった3つでした。

> 下記が別セッションで［AI］に引き継げるように提案してもらった内容！

引き継ぎ書を手で書いてコピペしていた（セッションを分けて作業するのが定着していた）。

> geminiにレビューしてもらったよ。
> 妥当か判断よろしく！

「レビュー」という語が17回。外部AIのレビューを貼って、採否を毎回ゼロから判定していた。

> ちなみにこのgmailでの一覧の設定（プロジェクト作成から認証まで）、
> 正直なんのためにやったのかピンと来ていないので、
> すごくわかりやすく説明してほしい。なぜ必要だったのか。

外部サービスの初期設定の伴走。これが一番回数が多くて、しかも「手順は終わったが理解していない」という状態が言語化されていました。

外れ方が対称ではないのが面白いところで、存在しない需要を3つ書いていた（偽陽性）だけでなく、毎週やっている作業を3つ取りこぼしていた（偽陰性）。自分の記憶に残るのは珍しくて難しかった作業のほうで、手順化すべきなのは退屈で繰り返しているほうでした。

ついでに白状しておくと、このとき候補リストから消したのは2件だけでした。`/commit-push-pr` は0回のまま残っていて、今も候補欄に居座っています。せっかく検出したのに3分の1を取りこぼしていました。

## まとめ

- 会話は `~/.claude/projects/` に全文残っている。Claude Code を使っている人全員の手元にある
- `type === "user"` だけでは足りない。8割以上はツールの実行結果。さらにエントリを絞ったあと、ブロック単位でもう一度弾く。エディタが送る状態通知が、自分の隣のブロックに並んでいる
- 出力には顧客名も認証情報も混ざる。リポジトリの外に出す
- 数字を出すときは「どう数えたか」も一緒に残す。手元では、方法の差が削除の差の3倍あった
- 保持期間は既定30日。ただし判定はファイルの更新日時（mtime）なので、「直近30日ぶんの会話」ではない。実際、74日前から始まる会話が丸ごと残っていた

ログを読むと勘より正確なことが分かる、というところまでは想像どおりでした。想像していなかったのは、そのログのほうも黙って形を変えていたことです。
